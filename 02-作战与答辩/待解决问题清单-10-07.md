## 二、P1 —— 答辩前必须准备好说法（多数不必改代码）

### 2.1 来自「天气赛道竞赛 + 开源项目」调研的问题

| # | 问题 | 会被怎么问 | 准备好什么 |
|---|---|---|---|
| P1-1 | **「首创」叙事站不住** | 「这个点子别人没做过吗？」 | GitHub 上已有一批几乎同题项目（FluxShield / ayveHacks / DevTrails-GigInsurance / swiftsure / SafeEats），商业上 **Arbol** 有「高累计降雨」参数化险，国内农险与巨灾指数保险早有先例。→ **一律改口径为「可验证」**：它们的判定是后端算一个比率、赔付是后端调支付网关，**只有我们是第三方可逐字节复算、且不需要运营方按键** |
| P1-2 | **阈值口径与国标不一致** | 「50 毫米为什么？和国标什么关系？」 | 背下：国标 `GB/T 28592-2012` **暴雨 = 12 小时 30.0–69.9mm 或 24 小时 50.0–99.9mm** → **50mm 只有配 24 小时窗口才等于暴雨**；我们窗口 1–72h 可调，所以 72h 那条线实际相当于 150mm。**主动承认**这是缺口，给出「按气象预警信号分档」的路线图（见 §三） |
| P1-3 | **只有"天气侧"数字，缺"影响侧"实证** | 「雨有多大我们知道，可骑手损失多大？」 | 用已核实的二手证据：HBR 2024（沪杭 1272 名骑手 / 58 万单）**热浪日延迟率 +21.8%、每小时仅多挣约 1 元，两个月额外收入约 545 元 vs 健康成本约 501 元**；泰国骑手研究**雨天配送事故 OR = 6.79**；西安 1473 起骑手事故研究**路面潮湿 +22.04%**。**并如实说明：暴雨对骑手"收入"的定量研究没找到** —— 这既是我们最薄的一块证据，也是选题空间 |
| P1-4 | **竞赛指标不对口** | 「你们为什么不用 RMSE / ETS 这类指标？」 | 天气赛道全是**预测**任务（阿里云 2018 用 ETS、雅安人机赛用 YPSI、Weather4cast 用累积降雨量、IEEE GRSS 用 F1）——**我们不做预测，输出的是离散决策**。对标方式是 **ETS 思路（该赔的赔、不该赔的不赔）**，不是 RMSE。可以说：预测越准，参数化保险越难成立（见 P1-5） |
| P1-5 | **检索缺口要如实标注** | — | 知网/万方付费墙 → 中文"极端天气×骑手"实证多见摘要；`GB/T 46862-2025` 全文需登录，网传"暴雨熔断"**无法核实，一律不引用**；平台内部数据无一手文件；**未检索到专门面向"骑手×天气"的竞赛**（空档本身可作选题正当性） |

### 2.2 来自《可行性判定 · 五问》的问题

| # | 问题 | 结论 | 准备好什么 |
|---|---|---|---|
| P1-6 | **参考对象搞错了** | 政策性农险锚的是**赔付率**（70%–75%），不是「杠杆」；`杠杆 L = 赔付率 ÷ p` 只是它的函数 | 答辩时别再讲「参考农险定杠杆」。⚠️ 农险综合赔付率的具体口径**尚未核实**，材料里只说"约 70–75%"并标注待核 |
| P1-7 | **逆选择（最容易被专业评委击穿）** | 静态定价 + 可以立刻投保 = 投保人可以看着预报决定买不买；**调杠杆只改门槛，不消除套利**；而且**预报越准，这个产品越难作为保险存在** | 主动承认，并给三条缓解路径（代价从高到低）：定价随预报浮动 → **购买时滞 t+N** → 限购 + 保额上限。**最有力的现实对照：农险通行做法是"播种前提前卖整季"**，所以 t+3 不是打补丁，是把产品拉回这类保险的本来做法 |
| P1-8 | **骑手身份认定：纯链上不可行（唯一"不做就不成立"）** | 现在任何人付钱都能买 → 违反**保险利益原则**与**损失补偿原则**，产品在法理上更接近**对赌**而不是保险；身份信息只有平台有 | **主动说出来**（别等问），给路径：**平台作为投保人/代理人（B2B2C）+ 平台签名凭证**；纯链上 DID 不可行 |
| P1-9 | **单阈值二元赔付，与预警信号天然分档不对齐** | 五问判定：**分档完全可行**，且正好修掉 P1-2 | 把它写成**路线图页**（不是今天改合约）：蓝色 12h 达 50mm → 25%、黄色 6h 达 50mm → 50%、橙色 3h 达 50mm → 75%、红色 3h 达 100mm → 100% |
| P1-10 | **t+3 购买只解决一半** | 技术上就一行 `require`；削掉短期预报优势，**削不掉气候尺度优势**；代价 = 实用性下降 / 资金占用（未起保退保 + 准备金计提）/ 状态机重画 | 讲成路线图 + 代价清单，别讲成"我们已经解决了" |

### 2.3 来自代码/链上自查的问题（都要主动说，不等评委问）

| # | 问题 | 事实 |
|---|---|---|
| P1-11 | **`claim()` 没有权限修饰符** | `03-合约/RainDeliveryInsurance.sol:243` `function claim(uint256 policyId) external notPaused` —— 任何人都能帮骑手触发赔付。**这是卖点（不需要运营方按键），也是风险（需要有资金池纪律）** |
| P1-12 | **`reserve` 没有自动规则** | 守卫存在（`amount ≤ balance − reserve`），但 `reserve` 默认 0、只能人工 `setReserve`；**缺的是"随在保敞口自动调整"的规则** |
| P1-13 | **合约 `sources` 字段从未写入** | `submitJudgement` 的签名里没有 `sources` 参数 → 链上读到的采信源数**恒为 0**，源数只存在留痕 JSON 里 |
| P1-14 | **保费不随保障时长变化** | `buyPolicy` 只校验 `msg.value == premiumOf(regionId)` → 理性投保人必选 72h（期限套利），承保组合的风险实际锁定在 72h 那一列 |
| P1-15 | **赔付额固定、与真实损失不挂钩** | `PAYOUT = 0.01 ether` 写死 → 属于"定额给付"，不是"补偿损失"（这一条与 P1-8 是同一个法理问题的两面） |

## 三、核心设计：「AI × Blockchain」到底怎么结合

### 先说一个错误的做法（很多人会这么做）

❌ 做一个 AI 模块，再做一个区块链模块，两个并排放在一个页面里。
→ 这是**拼贴**，不是结合。评委一眼看穿，赛道结合度拿不到高分。

### 再说正确的做法：让区块链去解决 AI 的信任问题

**问题**：AI 判定「这个片区确实发生了配送损失」——**凭什么信它？**

| 怀疑点 | 现实的麻烦 |
|---|---|
| AI 是黑箱 | 它为什么这么判断？说不清 |
| 输出可以被改 | 后台改一个数字，没人知道 |
| 事后扯皮 | 你说你判了，我说我看到的不一样 |

**解法（这就是结合点）**：

```
AI 读多源数据 → 输出「损失判定 + 置信度」
        ↓
把 ①输入数据的哈希 ②AI 输出的哈希 ③模型/提示词版本  →  一起写进合约
        ↓
合约据此决定：放行赔付 / 拒绝赔付
        ↓
任何人都能：拿原始数据自己算哈希 → 对得上；
            自己重跑一遍 AI → 结论一致
```

**一句话**：**把「你信不信我」变成「你自己验」。**

> 💡 这正好打在手册写的「**可信数据和安全验证**」上，
> 也正好是你报名第 11 题自己写的那个问题：
> **「AI 越来越会做决定，我们凭什么相信它？」**

### 落成代码长什么样（40 小时做得完）

**合约侧新增**（这就是清清楚楚的「赛期新增」）：

```solidity
struct Judgement {
    bytes32 inputHash;     // 多源数据快照的哈希
    bytes32 outputHash;    // AI 判定结果的哈希
    uint8   confidence;    // 0-100 置信度
    uint64  judgedAt;
    string  modelVersion;  // 模型 / 提示词版本
    bool    exists;
}

mapping(uint256 => Judgement) public judgements;   // policyId => AI 判定

function submitJudgement(uint256 policyId, bytes32 inHash, bytes32 outHash,
                         uint8 conf, string calldata ver) external onlyOperator;

// claim() 里加两条 require：
//   require(judgements[policyId].exists, "no AI judgement");
//   require(judgements[policyId].confidence >= MIN_CONFIDENCE, "low confidence");
```

**脚本侧新增**：AI 判定脚本（读天气 + 订单数据 → 调模型 → 输出结构化判定 → 上链）

**前端新增**：一张「AI 判定」卡片 —— 显示输入数据、判定结论、置信度、**以及一个「自己验证」按钮**
（按钮点开后：显示原始数据 + 哈希 + 让用户自己核对）

> 这个「自己验证」按钮是**演示时的杀手镜头** —— 它把抽象概念变成一个动作。

### 关于「多源数据」的现实做法

40 小时做不了四个真实数据源。**建议实做一个、其余诚实标注**：

| 数据源 | 怎么做 |
|---|---|
| 气象（降雨） | ✅ **已经接好了**（Open-Meteo，真实可直连） |
| 订单量骤降 | 用**公开数据或构造的合理数据**，材料里如实注明 |
| 路面积水 | 同上，或仅作为 AI 提示词里的一个信号位 |
| 骑手群抱怨（非结构化文本） | ✅ **这个最容易做真** —— 几条真实语气的文本，让 AI 做情感/事件抽取，**演示效果最好** |

> 诚实原则：**「实做了 2 个，另外 2 个是构造数据，接口已经留好」** 比
> 「我们接入了四个数据源」被戳穿要好一万倍。

## 2. 五个维度，以及为什么是这五个

| 维度 | 取值 | 为什么它必须进价格 |
|---|---|---|
| **地区** | 武汉 / 上海 / 北京 / 广州 / 成都 | 触发概率差 **5.9 倍**（72h 无条件：广州 1.276% vs 北京 0.216%）。同一场雨在不同城市的"值多少钱"完全不同 |
| **保障时长** | 24h / 48h / 72h | 窗口越长、累积雨量越大；v2 的档线是**线性**缩放（`50 × h/24`），于是档 2 的 `250 × h/24` mm 在 11 年逐小时历史里**一次都没触发过**（见 §6）——写在合约里但永远赔不到的条款。v3 把档线改成随时长**次线性**缩放。另外 v2 的 **24h 列多数格触到保费地板 0.0002**，短端被地板压平了 |
| **用户类型** | 众包自助 / 认证骑手 / 平台团体 | 决定**择时能力 κ**。这是全表最大的价格杠杆：成都 72h 从 κ=0 的 0.00036 到 κ=1.0 的 0.00185，**5.1 倍** |
| **使用场景** | 自助投保 / 平台代付 | 平台代付走**批量价**（一次 AI 判定覆盖整批），自助投保每份各触发一次判定 → 固定成本差 204 倍 |
| **购买量** | 1 / 10 / 50 / 100 / 500 / 1000 份 | 同上，把"判定 gas"这个固定成本按份摊薄。**微保险里固定成本常常大于风险保费本身** |

### 2.1 维度之间不是独立的乘数

地区、时长是**概率维度**；用户类型、使用场景、购买量是**机制维度**。做成两个独立乘数会把同一份逆向选择算两遍（例如"认证骑手"和"平台代付"高度相关，因为它们本就是同一个平台合约的两个条件）。

所以 v3 用一张**合法性表**：`(用户类型, 使用场景)` 6 种组合里只有 4 种合法，每种给一个 κ：

| seg | 用户类型 | 使用场景 | κ | 说明 |
|---|---|---|---|---|
| 0 | 平台团体 | 平台代付 | **0.00** | 平台整批为在册骑手投保，投保时点与天气无关 —— 择时归零，唯一"干净"的渠道 |
| 1 | 认证骑手 | 平台代付 | **0.15** | 认证 + 平台代付结算，个人择时只剩微弱残差 |
| 2 | 认证骑手 | 自助投保 | **0.55** | 身份绑定 + ≥3 天冷静期，削掉短期择时，削不掉"雨季才想起来买" |
| 3 | 众包自助 | 自助投保 | **1.00** | 无身份绑定、随时可买 —— 纯靠气候学"只买雨季"就能拿到的上限 |

非法组合：`(平台团体, 自助投保)`、`(众包自助, 平台代付)`。理由：团体单必须由平台发起；没有身份绑定的个人不能享受平台代付的批量价（否则"凑单"会成为新的逆向选择口子）。

### 2.2 κ 的含义与建模

κ 不是"打折系数"，是**投保时点的月度分布与风险月度分布的耦合强度**：

```
w_m = (1-κ)/nM + κ · rate_m / Σrate        （nM = 132 个月，rate_m = 该月触发率）
```

κ=0 → 各月等权（投保时点与天气无关）；κ=1 → 投保集中在高风险月份。

⚠️ **不能用 `rate_m^κ`**。干季 `rate_m = 0` 时 `0^κ = 0`，等于把全部干月权重清零，于是 κ 只有 0.15 也会给出 **18 倍**加载（幂律在零点处不连续）。线性混合式的上界是 `Σrate²/Σrate ≤ max_m rate_m`，加载倍数天然有界。

实测加载倍数（vs 无条件 p）：

| 区域 | 24h κ=0.15 / 0.55 / 1.00 | 72h κ=0.15 / 0.55 / 1.00 |
|---|---|---|
| 武汉 | 2.46× / 6.37× / 10.77× | 3.75× / 11.09× / 19.35× |
| 上海 | 1.84× / 4.10× / 6.63× | 2.51× / 6.54× / 11.08× |
| 北京 | 2.48× / 6.48× / 10.98× | 4.50× / 13.89× / 24.46× |
| 广州 | 1.63× / 3.32× / 5.22× | 2.01× / 4.69× / 7.70× |
| 成都 | 2.83× / 7.74× / 13.27× | 6.46× / 21.08× / **37.52×** |

### 2.3 考虑过、但没进价格的维度：骑手班次时段

"使用场景"最自然的延伸是**骑手一天里的班次**：10:00–20:00 跑单的人，凌晨三点的雨对他没有收入影响。既然合约赔的是"窗口内累计降水"，那按时段定价理论上能便宜很多。**我们算过，结论是它非但不便宜，而且更贵。**

算法：只累计班次内的雨量，档线**按班次小时数占窗口的比例等比缩放**（10h/24h → ×0.417；4h/24h → ×0.167）。这不是随便挑的缩放 —— 这正是合约自己 `thresholdOf(hours) = 50 × h / 24` 的缩放方式，也是"平均每小时强度不变"的含义。

| 城市 | 时长 | 全天触发 | 长班 10–20 | 比值 | 高峰 4h | 比值 |
|---|---|---|---|---|---|---|
| 武汉 | 24h | 0.7624% | 1.0030% | **0.8×** | 1.3380% | **0.6×** |
| 武汉 | 72h | 0.8105% | 0.8136% | **1.0×** | 1.2256% | **0.7×** |
| 上海 | 72h | 0.9101% | 1.0409% | **0.9×** | 1.3325% | **0.7×** |
| 北京 | 72h | 0.3497% | 0.2044% | **1.7×** | 0.5023% | **0.7×** |
| 广州 | 24h | 1.4200% | 2.7331% | **0.5×** | 3.3233% | **0.4×** |
| 广州 | 72h | 2.1855% | 4.4510% | **0.5×** | 4.5101% | **0.5×** |
| 成都 | 72h | 0.5811% | 0.5095% | **1.1×** | 0.7908% | **0.7×** |

（完整 15 行见 `tod-sensitivity.json`；"比值" = 班次口径 ÷ 全天口径，**< 1 表示班次口径触发得更频繁**。）

**读法**：比值落在 **0.4× ~ 1.7×**，多数 ≤ 1 —— 也就是说，"只赔我上班那几个小时"这个听上去对我们更省的想法，**实际触发概率与全天口径同量级，还常常更高**。原因是雨本来就集中在几个小时里下：把窗口缩短、档线也等比降低之后，后者降得比前者快。

为什么班次时段的雨量占比（下表）不足以补偿：**已赔付窗口里，班次时段雨量占全天雨量的中位数只有 25.0%~46.1%**，而缩放的档线要求它承担 41.7%（长班）—— 两个数几乎抵消。

| 城市 | 时长 | 班次雨量占比 中位 / P10 / P90 | 占比 < 25% 的赔付窗口 |
|---|---|---|---|
| 武汉 | 72h | 30.2% / 24.0% / 57.3% | 16.8% |
| 上海 | 72h | 37.7% / 22.7% / 48.4% | 12.1% |
| 北京 | 72h | 34.9% / 8.6% / 67.3% | 39.5% |
| 广州 | 72h | 46.0% / 27.9% / 67.1% | **3.9%** |
| 成都 | 72h | 27.5% / 14.6% / 42.3% | 46.1% |

**所以时段不进价格，理由有两层，第二层更重要：**

1. **第一层（够不够）**：算了才知道它不便宜。反过来如果它便宜 5 倍，我们会被诱惑去卖一个"我上班时淋到才赔"的东西 —— 而那个东西恰好是**能靠自述班次来择时**的，和 §7 删掉的临灾档一个毛病。
2. **第二层（该不该）**：**参数化保险的赔付标的是"区域事件"，不是"个人暴露"。** 我们卖的是"这场雨客观上够得上灾害级"，那是我们唯一能证明、也唯一能公开验证的东西（第三方拿区域降水数据就能复算）。赔付与个人是否出车无关，这不是精度不足，是产品定义。要按个人暴露赔，前提是**平台对班次的 attestation** —— 与身份认定是同一个依赖（`雨证-可行性判定-五问.md` 第三问）。

## 3. 核心公式

每一格的价格由两个数取大，再量化到网格：

```
C(N, q) = JUDGE_GAS / N + PAYOUT_GAS · q            每份的链上执行成本
P_net   = ceil((E₉₇.₅ · PAYOUT_MAX + C(N,q)) / R*)  费率闸 —— 让"97.5% 分位情形"下的赔付率不超过 R*
F       = ceil(C(N,q) · (1 + M))                    成本地板 —— 覆盖执行成本 + 25% 加成
P(N)    = max(P_net, F)
```

| 常量 | 值 | 依据 |
|---|---|---|
| `PAYOUT_MAX` | 0.01 ETH | 合约 `PAYOUT_MAX`，三档中最高档（100% 档、大暴雨）全额赔付额 |
| `R*` | 60% | 目标赔付率。与 v2 的 `TARGET_LOSS_RATIO` 一致 |
| `E₉₇.₅` | 逐格分位数 | 月聚类块自举 4000 次（块长 = 1 个日历月，保留月内自相关），取 97.5% |
| `M` | 25% | 成本加成 |
| `JUDGE_GAS` / `PAYOUT_GAS` | 0.00013 / 0.00012 ETH | 2026-10-06 真链实测 |
| 网格 | **0.00001 ETH** | v2 的 0.0001 太粗：平台批量价落在 0.00002~0.0001，0.0001 网格会吞掉一半折扣 |
| `MIN_PREMIUM_ABS` | 0.00002 ETH | 合约硬地板（v2 是 0.0002，**必须降到 0.00002**，否则批量价全被拒） |
| `PREMIUM_CAP` | 0.002 ETH | **尊严上限** = 赔付上限的 20%。见 §5 |

**`P(N) = max(P_net, F)` 是全文最重要的一行。** 微保险里固定成本常常大于风险保费：零售口径每份固定成本 0.00013051 ETH，而平台团体渠道 15 格的 97.5% 风险保费只有 0.00003692~0.00019083 ETH —— **固定成本是干净渠道风险保费的 0.7~3.5 倍**。只按风险定价会卖一份亏一份；只按成本定价会在大灾城市赔穿。

> 关于网格：`CEIL_TICK` 从 `1e4` 改成 `1e5` **偏离了本仓 `audit_numbers.js` / `tier_design_b2b.js` 的既有约定**（那两处是 0.0001，服务于 v1 单点定价）。理由是批量价量级低于网格分辨率。零售价四舍五入到 0.0001 与 v3 值一致，差异只体现在批量档。

## 5. 三个格不卖 —— 这是结论，不是缺陷

| 区域 | 时长 | seg | 若开卖的公平价 | 为什么 |
|---|---|---|---|---|
| 武汉 | 72h | t0c0 众包自助 | 0.00205 | > 尊严上限 0.002 |
| 广州 | 72h | t0c0 众包自助 | 0.00211 | > 尊严上限 0.002 |
| 成都 | 72h | t0c0 众包自助 | 0.00287 | > 尊严上限 0.002 |

**尊严上限 0.002 ETH**（按 1 ETH ≈ 25,000 元折算约 50 元），是赔付上限的 20%。`sellable = P(1) ≤ PREMIUM_CAP`。

不卖的格全部落在同一个组合上：**没有身份绑定 + 雨季城市 + 最长时长**。含义很直白 —— 如果你不给这单加任何可追溯的约束，那么"成都 72 小时暴雨险"的诚实价格是 0.00287 ETH，是赔付额的 28.7%，也就是**骑手每交一份保费里有近三成是纯风险成本，剩下的是因为别人会挑时间买**。这个价格卖不动，也不该卖。

**这三格就是"认证换价格"的产品故事**：同样是成都 72h，平台团体 0.00036、认证自助 0.00185、无认证 —— 不卖。**身份验证不是合规动作，是价格动作。**

## 6. 档线必须随保障时长缩放（v3 修掉的 v2 硬伤）

v2：`thresholdOf(hours) = 50 × hours / 24`，三档 = `[50h/24, 100h/24, 250h/24]`。

**问题**：档 2 的 250×(h/24) 在 11 年实测里几乎不可达。72h 要 750mm、48h 要 500mm —— 武汉 11 年最大 72h 累计远低于此。**这是"合约里写了一个永远不会赔付的条款"**，对骑手是虚假承诺。

v3 改为**分档线和档位金额都随窗口走**：

| 时长 | 档 0 起点 | 档 1 起点 | 档 2 起点 | 档位金额 |
|---|---|---|---|---|
| 24h | 50mm | 100mm | 130mm | 50% / 75% / 100% |
| 48h | 75mm | 125mm | 175mm | 同上 |
| 72h | 100mm | 150mm | 190mm | 同上 |

依据：三档分别对应 GB/T 28592-2012 的暴雨 / 大暴雨量级在对应窗口内的可达值，且 72h 档线不要简单 3 倍于 24h（实测 72h 累计降水不是 24h 的 3 倍，因为雨事件本身有时长上限）。

## 7. 为什么删掉了"临灾加保"这一档

早期草稿里还有第 6 格：`(认证骑手/众包, 预警增保)`，定价用条件触发率 `P(触发 | 投保前 24h ≥ 25mm)`。**v3 删了它**，三条理由：

**① 合约的冷静期在生产口径下已经把它锁死了。** `RainDeliveryInsuranceV2.sol:228` 写的是 `p.effectiveFrom = block.timestamp + coolingPeriod;`（`:68` 合约**默认** `coolingPeriod = 3 days`，operator 可改）。冷静期只要 ≥ 最长保障期 72h，"看到橙色预警再买"的保单**整个保障窗都还没开始**，这场雨已经过去了。**这不是靠加价挡的，是结构上盖不住。**

> ⚠️ **必须说清版本**：`968` **演示链上 `coolingPeriod` 被设成了 `0`**（`04-脚本/rehearse-v2.js:228` 会把非 0 的值改掉，现场才能演示"买 → 喂价 → 判定 → 索赔"一条动线；这是 operator 可配开关，带 `CoolingPeriodSet` 事件）。**所以第 ① 条是"生产默认值"的性质，不是 968 这条演示链的性质。** 我们能站住的说法是：**合约已具备把冷静期设到 ≥ 保障期的能力，生产建议 ≥ 6h～3 天（`B端档位设计与不亏损证明.md:216` 四-D），演示链为了动线连贯设 0。** 反过来说，**只靠 ① 不够，真正让这一档不值得做的是 ② 和 ③。**

**② 这个维度不可核验。** "我是在预警期内买的"是买方自述，合约看不到。而任何能被自述的参数，一定会被选成对买方最便宜的那个 —— 给一个不可核验的维度定价等于没定价，只是给自己一个虚假的安全感。

**③ 定量上它根本不是主要威胁。** 实测（见 `定价体系-v3-数表.md` §五）：

| | 加载倍数 |
|---|---|
| 临灾择时（前 24h 已累计 ≥25mm） | **5.35× ~ 12.29×** |
| 季节择时（只买雨季，**零预报能力**） | **5.22× ~ 37.52×** |
| 两者谁更强 | 季节强 12/15 格，临灾强 3/15 格（全部在 24h 档） |

**"买雨季"是一个人人可查的公开信号，不需要任何预报能力，却比"看到预警再买"更值钱。** 所以正确的应对是：把预算花在**身份绑定 + 冷静期**上（这两条同时压制季节择时和短期择时），而不是给一个不可核验、且次要的维度设一档价。

临灾条件率仍然逐格算出并存档，但**只作为诊断量，不进入任何报价**。

## 11. 诚实边界（写进对外材料时必须带）

1. **κ 与所有概率都是历史频率，不含预报技能。** 真实买家能拿到的信息比这更多，所以本表是最保守的一侧。
2. **月聚类块自举的块长固定为 1 个日历月**，与真实风险记忆尺度不同，只做参数不确定性的一阶修正。
3. **本表未含冷静期造成的生效延迟**。v2 默认 3 天 ≥ 最长保障期 72h，意味着任何"临时追保"都盖不住当次天气 —— 方向上让本表更保守。
4. **`JUDGE_GAS` / `PAYOUT_GAS` 是 Sepolia 2026-10-06 的真链实测值**，主网 gas 价格不同则需重算。
5. **κ 的四个取值是设计参数，不是拟合结果。** 它们表达的是产品约束（有没有身份绑定、有没有冷静期、是不是平台整批发起），不是从数据里回归出来的系数。数据只用来算"给定 κ 下的期望赔付"。
6. **不构成精算意见。** 这是赛事原型，未做偿付能力评估、未考虑巨灾相关性、未做再保险安排。
